================================================================================
                    DevOps Orchestra Project Documentation
================================================================================

OVERVIEW
--------
DevOps Orchestra is a comprehensive, multi-agent AI-powered DevOps automation 
platform that orchestrates the entire software delivery lifecycle. It provides
end-to-end automation from code validation and infrastructure provisioning to 
testing, deployment, monitoring, and recovery. The system is built on an 
event-driven architecture using Kafka for agent communication, with each agent
specialized in distinct DevOps functions.

================================================================================
                                ARCHITECTURE
================================================================================

CORE CONCEPTS
-------------

1. Event-Driven Architecture
   - All agents communicate via Kafka topics
   - Loose coupling between agents
   - Scalable and resilient system
   - Asynchronous processing

2. Stateful Orchestration
   - Shared DevOpsAgentState object
   - Context-aware decision making
   - Agent handoffs with state preservation
   - Pydantic models for type safety

3. Config-Driven Pipeline
   - devops_orchestra.yaml configuration in each repository
   - Defines build, test, deployment, and observability preferences
   - Flexible customization per project

4. LLM-Powered Code Generation
   - Auto-generates Dockerfiles, Terraform files, and tests
   - Uses Groq API with LLaMA-3.3-70B model
   - Context-aware code generation
   - Template-based prompt engineering

TECHNOLOGY STACK
----------------

Infrastructure:
- Docker & Docker Compose for containerization
- Kafka + Zookeeper for message bus
- Flask for webhook server
- FastAPI for tool server
- Python 3.9

AI/ML:
- Groq API (LLaMA-3.3-70B-Versatile model)
- LangChain for orchestration
- LangGraph for workflow management

DevOps Tools:
- Terraform for Infrastructure as Code
- Docker for container builds
- Git for repository management
- Maven, Gradle, npm for build tools

Communication:
- Kafka for event streaming
- REST APIs for tool invocation
- Slack integration for notifications
- GitHub webhooks for triggers

   - clone_repo: Git repository cloning with branch support

2. KAFKA EVENT BUS
================================================================================

ARCHITECTURE
------------
The system uses Apache Kafka as the event streaming platform for all 
agent communication. Each agent publishes events to specific topics and 
consumes from relevant topics.

KAFKA TOPICS
------------

1. code_push
   Description: Triggered when new code is pushed to repository
   Publisher: GitOps Agent
   Consumers: Code Analysis Agent, Build Agent, Infrastructure Agent
   Event Schema: CodePushEvent

2. code_analysis
   Description: Emitted after static code analysis completes
   Publisher: Code Analysis Agent
   Consumers: None (used for monitoring)
   Event Schema: CodeAnalysisEvent

3. build_ready
   Description: Emitted when build completes (success or failure)
   Publisher: Build Agent
   Consumers: Test Agent
   Event Schema: BuildReadyEvent

4. test_results
   Description: Emitted after test execution completes
   Publisher: Test Agent
   Consumers: None (used for monitoring)
   Event Schema: TestResultsEvent

5. iac_ready
   Description: Indicates infrastructure provisioning is complete
   Publisher: Infrastructure Agent
   Consumers: Deployment Agent
   Event Schema: IaCReadyEvent

6. deployment_triggered
   Description: Signifies deployment has been started or completed
   Publisher: Deployment Agent
   Consumers: None (used for monitoring)
   Event Schema: DeploymentEvent

7. observability_alert
   Description: Alert based on monitoring/metrics anomalies
   Publisher: Observability Agent (planned)
   Consumers: Rollback Agent (planned)
   Event Schema: ObservabilityAlertEvent

8. rollback_event
   Description: Issued when rollback is initiated
   Publisher: Deployment Agent, Rollback Agent
   Consumers: Rollback Agent
   Event Schema: RollbackEvent

EVENT SCHEMAS
-------------
All events are defined as Pydantic models in shared_modules/kafka_event_bus/

StatusEnum:
- success: Operation completed successfully
- failed: Operation failed
- in_progress: Operation in progress

SeverityEnum:
- info: Informational messages
- warning: Warning conditions
- critical: Critical conditions

================================================================================
5. CONFIGURATION FILE (devops_orchestra.yaml)
================================================================================

STRUCTURE
---------
Every repository must contain a devops_orchestra.yaml file in the root 
directory. This file defines the complete DevOps pipeline configuration.

SECTIONS
--------

1. project
   - name: Project name
   - frontend-language: Frontend stack
   - backend-language: Backend stack
   - repo: Repository URL

2. build
   - tool: docker, maven, npm, poetry, gradle
   - context: Build context path
   - dockerfile: Dockerfile path

3. testing
   - enabled: true/false
   - framework: pytest, unittest, npm, maven, etc.
   - command: Custom test command

4. deployment
   - type: cloud, kubernetes, etc.
   - provider: aws, azure, gcp
   - strategy: blue-green, canary, standard
   - region: Cloud region
   - services: List of services to deploy
     * name: Service name
     * runtime: ec2, lambda, fargate
     * port: Service port
     * env: Environment variables

5. infrastructure
   - tool: terraform, cloudformation
   - path: Directory containing IaC files

6. secrets (optional)
   - manager: aws_secrets_manager, azure_keyvault
   - keys: List of secret keys

7. rollback (optional)
   - enabled: true/false
   - threshold:
     * cpu: CPU threshold percentage
     * errors: Error count threshold
     * duration: Time threshold

8. observability (optional)
   - enabled: true/false
   - tools: List of tools (prometheus, grafana, cloudwatch)
   - alerts: List of alert configurations

9. chatops (optional)
   - enabled: true/false
   - platform: slack, teams
   - channel: Channel name
   - notify_on: List of events to notify

EXAMPLE CONFIGURATION
---------------------
```yaml
project:
  name: my-app
  frontend-language: react
  backend-language: python
  repo: https://github.com/user/my-app

build:
  tool: docker
  context: .
  dockerfile: Dockerfile

testing:
  enabled: true
  framework: pytest
  command: pytest tests/

deployment:
  type: cloud
  provider: aws
  strategy: blue-green
  region: us-west-2
  services:
    - name: api-server
      runtime: ec2
      port: 5000
      env:
        - key: ENV
          value: production

infrastructure:
  tool: terraform
  path: infra/

rollback:
  enabled: true
  threshold:
    cpu: 90
    errors: 5
    duration: 5m

chatops:
  enabled: true
  platform: slack
  channel: "#devops-orchestra"
  notify_on:
    - deployment_success
    - deployment_failure
    - rollback_triggered
```

6. PIPELINE FLOW
================================================================================

END-TO-END EXECUTION
--------------------

1. GITHUB WEBHOOK TRIGGER
   - Developer pushes code to repository
   - GitHub sends webhook to Flask server
   - GitOps Agent receives event

2. GITOPS AGENT EXECUTION
   - Validates event payload
   - Clones repository from GitHub
   - Validates devops_orchestra.yaml
   - Performs license audit
   - Calculates repository size
   - Updates DevOpsAgentState
   - Publishes CODE_PUSH event

3. CODE ANALYSIS AGENT (Parallel with Build)
   - Consumes CODE_PUSH event
   - Analyzes code files using LLM
   - Identifies errors, warnings, notes
   - Updates state.code_analysis
   - Publishes CODE_ANALYSIS event
   - If failed → sends notification and stops pipeline

4. BUILD AGENT
   - Consumes CODE_PUSH event
   - Reads build.tool from config
   - If Docker: generates Dockerfile if missing
   - Builds application using specified tool
   - Updates state.build_result
   - Publishes BUILD_READY event
   - On failure → retries (up to 3 times) or stops

5. TEST AGENT
   - Consumes BUILD_READY event
   - Generates tests using LLM
   - Executes tests with specified framework
   - Calculates pass/fail statistics
   - Updates state.test_results
   - Publishes TEST_RESULTS event
   - On failure → retries or continues to infra

6. INFRASTRUCTURE AGENT
   - Consumes CODE_PUSH event (parallel)
   - Generates Terraform files using LLM
   - Runs terraform init, validate, apply
   - Extracts infrastructure outputs
   - Updates state.infra
   - Publishes IAC_READY event
   - On failure → sends notification

7. DEPLOYMENT AGENT
   - Consumes IAC_READY event
   - Reads deployment configuration
   - Executes terraform apply for deployment
   - Monitors deployment status
   - Updates state.deployment
   - Publishes DEPLOYMENT_TRIGGERED event
   - On failure → triggers rollback

8. ROLLBACK AGENT
   - Consumes ROLLBACK_EVENT
   - Executes terraform destroy
   - Cleans up infrastructure
   - Updates state
   - Publishes rollback completion event

9. NOTIFICATIONS
   - Slack Agent monitors all events
   - Sends notifications on configured events
   - Provides deployment status updates
   - Alerts on failures

RETRY MECHANISM
---------------
- Build failures: Up to 3 retries
- Test failures: Up to 3 retries
- Other agents: Single attempt with notification

FAILURE HANDLING
----------------
- Code analysis failure: Stops pipeline, sends notification
- Build failure after retries: Stops pipeline, sends notification
- Test failure after retries: Continues to infra, sends notification
- Infra failure: Sends notification, stops deployment
- Deployment failure: Triggers automatic rollback

8. DEPLOYMENT AND OPERATION
================================================================================

DOCKER SETUP
------------
Location: Dockerfile, docker-compose.yml

Services:
1. zookeeper: Kafka coordination
2. kafka: Message bus
3. app: Main DevOps Orchestra application

Docker Compose Configuration:
- zookeeper: Port 2181
- kafka: Port 9092
- app: Port 5001
- Volumes: ./data/gitops_repos for repositories

ENVIRONMENT VARIABLES
---------------------
Required:
- GROQ_API_KEY: Groq API key for LLM access
- NGROK_AUTHTOKEN: ngrok token for webhook (optional)

Optional:
- All Slack output (logs, errors, success) uses the pipeline logs channel (SLACK_PIPELINE_LOGS_CHANNEL_ID or SLACK_PIPELINE_LOGS_WEBHOOK_URL)

INSTALLATION
------------
1. Clone repository
2. Copy .env.example to .env
3. Set GROQ_API_KEY
4. Set NGROK_AUTHTOKEN (optional)
5. Run: docker-compose up --build

STARTUP SEQUENCE
----------------
1. Wait for Kafka to be ready (max 120 seconds)
2. Create Kafka topics
3. Launch ngrok tunnel (optional)
4. Start tool server (FastAPI on port 8001)
5. Start combined agent (LangGraph)
6. Start Flask webhook server
7. System ready to receive GitHub webhooks

GITHUB WEBHOOK CONFIGURATION
-----------------------------
1. Go to repository settings
2. Navigate to Webhooks
3. Add webhook:
   - Payload URL: https://your-ngrok-url.ngrok.io/webhook
   - Content type: application/json
   - Events: Just the push event
   - Active: checked

LOCAL DEVELOPMENT
-----------------
1. Install dependencies: pip install -r requirements.txt
2. Start Kafka: docker-compose up kafka zookeeper
3. Install Terraform, Docker, Git locally
4. Run: python main.py

================================================================================
14. TROUBLESHOOTING
================================================================================

COMMON ISSUES
-------------

1. Kafka Connection Errors
   Solution: Wait for Kafka to fully start (120s timeout)
   Check: docker-compose logs kafka

2. Missing Tools (Terraform, Docker, Git)
   Solution: Install tools in Docker container or locally
   Check: which terraform, which docker, which git

3. LLM API Errors
   Solution: Verify GROQ_API_KEY environment variable
   Check: Test API key directly

4. Repository Clone Failures
   Solution: Verify webhook payload, check repository access
   Check: git ls-remote <repo-url>

5. Terraform Apply Failures
   Solution: Check generated Terraform files, verify cloud credentials
   Check: terraform validate, terraform plan

6. Tool Server Not Starting
   Solution: Check port 8001 availability
   Check: ps aux | grep tool_server

DEBUGGING
---------
1. Enable verbose logging
2. Check Kafka topics: kafka-topics --list
3. Inspect events: kafka-console-consumer
4. Review agent logs in state.agent_logs
5. Test individual tools via tool server
6. Validate configuration files manually
